# Fork

The canonical branch of this fork is `dev`. Deploy from `dev`, or from the working branch that will become `dev`. When that branch is finished and its tests pass, fast-forward it onto `dev`. Do not force-push.
Schema rebase: do not keep version numbers from the commits being replayed. On this base, upstream owns schema 40, 41, and 42. FirstMate is one migration at schema 43, the next number after upstream's latest. Do not put FirstMate into 40, 41, or 42. Do not split FirstMate into 43 and 44. Schema 44 is the heal for a recorded schema 42 that never added images_json. A recorded version does not prove its objects. If upstream edits the body of a version a database may already have recorded, keep that upstream block as written and add one object-check heal at the next integer. Do not expect `current < N` to re-run. Do not put that heal in the FirstMate migration.
GJC pin on an upstream merge: the merged pin in `packages/gateway/package.json` (`gjc.version`) is the newer of the fork's pin and upstream's pin by semver. Never keep the older one from either side. When upstream's pin is newer, the renewal is not done until three things hold. The lane-switch patch exists as `packages/cli/src/patches/gajae-code/<pin>-lane-switch.patch` and applies to that release with `patch --fuzz=0`, or it is dropped because that release ships the same lane switch. No doc, test, or skill still names the old pin as current. `/verify-firstmate` passes again on the test home with the new pin installed.
Keep each `.gjc/skills/verify-*/` skill honest with `/maintain-verification-skill`. One verification skill per app, with one feature file per user-facing behavior. A pass on one feature file does not cover the others. Do not edit product code to make a failed drive look passed.
