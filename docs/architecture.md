# Architecture

## Runtime layout

The Bun workspace is divided into small packages:

| Package | Responsibility |
|---|---|
| `@gajae-gateway/protocol` | Versioned NDJSON frames, negotiation, verb/event catalogues, and canonical origins. |
| `@gajae-gateway/sdk` | Client for the gateway’s Unix-domain socket or stdio transport. |
| `@gajae-gateway/gateway` | Daemon: configuration, SQLite state, sessions, delivery, memory, monitors, and the `gjc` boundary. |
| `@gajae-gateway/adapter-discord` | Discord ingress and outbound delivery, including typing hints and the reaction-gradient presence. |
| `@gajae-gateway/adapter-telegram` | Telegram ingress and outbound delivery. |
| `@gajae-gateway/adapter-slack` | Slack ingress over Socket Mode, mrkdwn delivery, reactions, working-status presence, and missed-message recovery. |
| `@gajae-gateway/cli` | Owner commands over the gateway socket. |

`bun run build` compiles the gateway, Discord adapter, Telegram adapter, Slack adapter, and CLI into standalone executables. The gateway's `GlobalGjcClient` is only a client of the same global-user GJC executable, canonical agent directory, and broker used by the operator's normal SDK. Matching the executable alone is insufficient: the service must resolve the same user profile and broker authority. GJC owns daemon startup and lifecycle; the gateway neither seeds settings nor owns, reaps, repairs, or garbage-collects the shared runtime. Every persona, worker, and monitor operation uses `SessionPort`; no per-turn `gjc --resume` process is spawned. Normal shutdown closes only the gateway's own SDK calls and relays, never the shared user daemon or its session hosts.

SQLite records one active broker authority and immutable gateway-created session bindings. Visibility in the user's SDK session list is not ownership: controls require positive creation/binding evidence under that authority, and unrelated user sessions must remain untouched. A populated database with a missing or mismatched authority requires explicit administrative cutover before recovery. Cutover preserves old history and quarantines accepted or unproven old work rather than replaying it in the new authority; old private-broker held lanes do not automatically become global-user lanes. See the operator runbook for the backup, census, and cutover boundary.

## Wire protocol and negotiation

Gateway clients exchange newline-delimited JSON frames over a Unix socket (or stdio). A frame has a profile version and a type: `hello`, `negotiated`, `request`, `response`, `event`, or `error`; an encoded frame is capped at 1 MiB.

A client must start with `hello`, listing `supportedVersions` and optionally `requiredCapabilities`. The Firstmate cutover supports only profile `1.1` and returns its capability list; there is no obsolete-profile fallback. Gateway, adapters, CLI, and SDK must upgrade together. No common version produces `incompatible_profile_version`; a missing required capability produces `missing_required_capability`. Unknown optional fields are ignored, while required capabilities are explicit compatibility checks. Requests then invoke catalogued verbs and asynchronous events include `chat.message`, `monitor.event`, and `gateway.stopping`.

## Conversation identity and sessions

The ordinary persona mailbox/reset behavior in this section does not override the mapped-task identity, no-replay, and retirement fences under [Worker lanes](#worker-lanes).

An origin is a validated, platform-neutral record: platform, kind, conversation ID, and (only where appropriate) parent or peer IDs. Platforms are `loopback`, `discord`, `telegram`, `slack`, and `monitor`; kinds include DM, channel, thread, topic, loopback, and monitor event type. `discord`, `telegram`, and `slack` are the *chat platforms* (`CHAT_PLATFORMS`): the only origins the message and reaction verbs accept, because only they have an adapter that can settle a delivery. Slack thread origins carry a `channel:ts` conversation id with the channel as parent; Slack has no `topic` kind. The only canonical identity string is `originKey`:

```text
platform/kind/conversationId[/parent=…][/peer=…]
```

Group `OriginRef`s may also carry optional, provider-neutral `boundaryId` metadata naming a containing policy boundary. It is fallback lookup metadata only: it does not alter `originKey`, replace the channel/thread origin, or apply to DMs.

It is opaque after creation—callers must not parse it back into fields. Each origin key has one persistent broker-hosted `gjc` session and an epoch. `/new` (and `/reset`) increments that origin’s epoch and binds the next turn to a new session, leaving other origins untouched. Session creation is idempotent and includes the gateway instance, normalized origin key, and epoch, so a crash around creation can safely retry while the broker remains live.

Inbound messages enter a durable per-origin mailbox actor that applies one rule: if a turn is running, the message is steered into it (`turn.steer`); if the origin is idle, the message is sent as the next turn, immediately. There is no settle window, no coalescing and no age-based expiry: an unanswered row stays `pending` until a turn takes it. Each turn binds its trigger row with a deterministic caller operation reference, the SDK session and a `dispatched_at` stamp before the send; an accepted receipt advances the turn independently of terminal completion. A steer failure never authorizes session replacement or discards the message. An authoritative refusal leaves the row pending until the current turn ends, then sends it as the next turn on the same session; if the turn has already ended, it is eligible for that next send immediately. Ambiguous receipts or transport failures retain the original `clientRef` for observation and same-reference reconciliation, never a new send or a new reference. Session replacement requires explicit operator `/new` (or `/reset`) or a separate, narrowly proven irrecoverable session condition; failed steering is never evidence of that condition and never creates a new epoch or retires the current turn. Session binding happens before any prompt is attached to the row; if a bind epoch's session-create key becomes `terminal_uncertain`, three consecutive bind failures rotate the epoch automatically, preserving every pending row and deriving a fresh idempotency key instead of leaving the channel permanently dead. Model selection also happens before send: a `model.set` failure releases the bound row back to plain pending rather than creating an ambiguous hold; an unavailable session rotates the epoch immediately, while other model failures retry with capped backoff. After send, a `bound` operation whose status remains `unknown` is held once; if the session is positively dead or is live with an empty prompt queue on the second sweep, it is safely requeued on a fresh epoch. An `accepted` operation is never released by that heuristic because it may already have produced side effects. The actor serializes admission, steering, tail frames, broker-generation changes, `/model` live controls, and `/new` fencing. A message the user edits after ingestion is not a new message: the adapter forwards it as `chat.edit` and the gateway streams it into the same session as `[MESSAGE POINTER: <messageId>] …` with the new body - steered into the running turn or sent as the next one by the same rule - while the context ledger's copy of the original is rewritten to the new body. An edit of a message the gateway never ingested is ignored, and the same edit event delivered twice is one update. The adapter keeps an edit that could not reach the gateway (link down, request failed) in a bounded outbox and replays it on the next connect, because message-history recovery cannot reconstruct an edit of an id it already knows. Each bound session has one resident `gjc sdk serve --stdio` relay that is the turn's whole transport: `turn.prompt`, `turn.steer` and `turn.result` go down its stdin as SDK control/query frames, and because the prompt was submitted on that connection the host streams the turn's own content back up it - `agent_start`, every assistant `message_end` (mid-work speech, delivered to the channel as it arrives), `tool_execution_*` (presence), and `agent_end` - stamped with the turn's `commandId`/`turnId`. Frames with another correlation are dropped; nothing is polled, paged, cursored or de-duplicated by text. A relay that dies mid-turn loses that turn's remaining content (host content is best-effort by contract); the turn then settles from `turn.result` status and its original-result body, and the handle reopens for commands. `session status` remains terminal authority. Different origins work concurrently, but same-origin persona, worker, and monitor requests use the shared `SessionPort` lock. A terminal failure generates a visible, ledgered notice carrying the runtime's own error code and message, truncated but never erased, with only secrets redacted:

```text
[turn failed] spawn_failed: SDK startup did not complete before readiness cutoff. Send /new to rebind this conversation.
```

The same string goes to the daemon log, so a channel transcript is enough to triage without shell access. The `/new` hint appears only when a rebind is plausibly the remedy.

`/model` applies `model.set` to the existing session through that mailbox; it neither changes the epoch nor truncates the transcript, and each subsequent persona turn logs its effective model. `/new` is the explicit recovery boundary: it atomically advances the epoch, fences stale output, and discards only pending messages not yet in a turn - the one path that completes an inbound row without answering it. Accepted prior-epoch turns retain their bound session identity as durable recovery holds, so a restarted actor can reattach status/tail until terminal reconciliation; the gateway never invents a replacement operation reference or aborts a running SDK turn.

Recognized provider-input/context failures also have a bounded **reset-next** path. Exact current-session provider evidence, rather than occupancy or generic failure text, authorizes one durable consecutive reset per origin. The failed trigger is completed without replay, and subsequent pending messages bind under the fresh epoch without changing the context floor or discarding queued traffic. Reset uses the existing native SDK session operations through `SessionPort`, restricted to positively owned gateway bindings under the current authority; it does not manage the shared broker or resubmit old accepted work. Per-trigger deduplication and the origin budget survive restart; an already-retired turn cannot rotate a newer session. Without complete execution-safety attestation from the runtime, the gateway never retries the failed operation merely because it reset the binding.

### Persistent-session observability

The daemon writes grep-stable fields for the persistent-session control plane: `steer_delivered originKey=… opRef=… messageId=…`, `steer_failed origin=… message=… action=recover` (reconcile the current turn and defer the refused row, never replace the session), `steer_ambiguous … action=replay` and `steer_hold … reason=transport_torn` (observe and reconcile the original `clientRef`, never submit a new send), `tail_frame_foreign session=… commandId=… turnId=… expected=…` (a frame on the relay that belongs to another turn, dropped), `tail_relay_lost session=… opRef=…` and `recovery_hold … reason=relay_lost_mid_turn` (the owned relay died; the turn settles by status), `stall_alert originKey=… sessionId=… silentMs=…`, `compaction_event sessionId=… originKey=…`, and `retired_hold originKey=… epoch=… opRef=…`. A stall is an operator alarm only; it never terminates a live operation. Broker-generation changes represent observed user-runtime changes, not gateway-owned daemon replacement. Historical `session_rebound_after_steer_failure` logs identify removed unsafe behavior, not the current recovery policy. A compaction event is observed from a tail frame or authenticated control receipt, never initiated as persona-turn orchestration.

### Worker lanes

**Firstmate Part 1 contract.** This owner-fork capability is integrated into Gajaeway, not a plugin, second run loop, or scheduler. The following requirements describe the implementation target, not deployed or crash-tested guarantees. GJC owns execution/session lifecycle and terminal truth; the gateway owns admission, durable task/thread/control bindings, ordering, observation, and report obligations; adapters own addressing and presentation. Reuse existing lane admission, internal `SessionPort`, observer recovery, DB transactions, coordinator admission, and delivery ledger. No private GJC lifecycle path, semantic progress API, or second observer authority is introduced.

One stable task assignment maps to one independent lane and one task thread; the persona remains the coordinator cockpit, not the executor in that thread. A task is a mandate and its obligations, not a second execution lifecycle. Turn terminal, mandate completion, report admission, report consumption, and physical delivery are separate facts. Ordinary unbound work APIs remain valid for unrelated work, but a task-bound lane cannot be retasked or use bare run/resume to bypass task admission. Coding completion is its own evidence admission: `final_admitted` records admission of the original report only, and completion is admitted solely from the exact reviewed result/diff together with an explicit integration target, authenticated owner approval, and combined verification evidence. Unresolved conflicts, failed checks, uncertain original identity, or pending approval leave completion pending; this evidence admission is not independent proof, executes no integration, and claims no merge scheduler, executor, or production verification.

The latest authenticated closeout instruction in the existing owner-control order governs the per-task integration target and question decisions. A review must reference that exact source; an older approval cannot be resurrected after a newer owner decision, and earlier answers are not combined to infer permission. Ordinary prose and coordinator/persona statements do not establish owner authority. No global target default or new approval ledger is introduced.

Persist original task/job/attempt/opRef/session/epoch and control/event/client references before transport. Same-identity duplicates converge without duplicate execution; conflicting duplicate payloads fail closed. The initial assignment is immutable; later authenticated owner instructions and decisions are separate source-linked records. Claim the task surface durably before creating its thread. An uncertain create/bind stays held: do not recreate by title, allocate replacement execution identities, or interpret recovered pre-binding messages as steering. A thread's one-task tombstone is permanent. Archive/reset/reopen is presentation only, never worker retirement or revival; an invalid mapping has no persona fallback.

Direct authenticated owner steering in the live mapped thread bypasses coordinator approval, not identity, ordering, or scope fences. Task-local scope is the default. Inferred impact elsewhere produces a suggestion only; explicit wider direction names targets and retains shared source correlation with independent sent/accepted/refused/held outcomes. Acceptance proves a transport disposition, not worker understanding or compliance. Persist the original control before sending and reconcile uncertain receipts through the narrow read-only `turn.steer_status` seam. Missing, stale, mismatched, or unavailable receipts remain held without resend. Administrative abandonment preserves debt and never unblocks later controls.

Mutation-capable (`code_mutating`) admission uses native GJC 0.18.8 managed worktree allocation: GJC provisions the dedicated checkout and the gateway validates and binds it. The gateway persists the original session-create key and target before effects, keeps the immutable source cwd distinct from the validated returned execution checkout, and validates repository identity, registered linked-worktree binding, and ownership on that returned checkout before any worker mutation. GJC's default nested `.worktrees` bucket is acceptable when it is a genuinely distinct registered linked checkout of the same repository and owned by this task — the primary checkout itself, the coordinator's identity, foreign repositories, and other tasks' checkouts are rejected — and the bucket must be Git-ignored by the repository (this repository ignores `/.worktrees`); no sibling placement policy or environment rollout is required. Uncertain bindings recover by lookup of the original create only; `not_found`, `conflict`, and `uncertain` never authorize replacement or duplicate execution, and no worktree or branch is deleted automatically. `read_only` and non-code tasks remain independent of Git integration, and `read_only` is an admission declaration, not an OS/credential sandbox. Typed `read_only`→mutating elevation must cross the pre-transport isolation gate: the task must already have eligible dedicated isolation, otherwise refuse elevation and require separately admitted isolated work. Never silently move or replay the old attempt.

Native GJC 0.18.8 normally chooses the primary checkout's HEAD as its worktree base. A divergent linked-source HEAD is refused rather than silently substituting that base. Source checkout identity and the original epoch/key/target are retained before effects; known-unsent source validation failures do not consume the create permission.

Actual Git registration, backpointer, repository and coordinator checks run in the required synchronous SDK-result admission callback before ownership. The internal store transaction independently validates the complete retained source/execution tuple and exclusive Git-directory/session ownership; it is not an RPC or a substitute for that Git admission boundary. Transport revalidates the retained proof. Provisioning remains GJC-owned.

**Task-local evidence and delivery.** The meaningful work log selects actual available assignment, control admission/outcome, proven checkpoint, hold/error, evidence pointer, and final records. It cannot fabricate intermediate progress, promote a commit observation to semantic success, or promise a full tool trace. Required control/error/final facts are not optional prose. Subsequent owner records link their original messages rather than needlessly mirroring them.

Persist immutable render payload and a stable correlated delivery intent atomically with each source transition using the existing transaction/CAS and delivery ledger. Revalidate destination binding and authorization before publication. Invalid/unavailable mappings hold detail rather than redirecting it to the cockpit or parent. One payload may be split into sequential text chunks; confirmation follows all chunks, not the first post. Whole-payload retries preserve logical identity and payload but may repeat previously posted chunks. Show possible duplication and preserve prior physical history: delivery is at-least-once, not exactly-once.

Keep the coordinator's 2048-byte UTF-8 envelope separate from the original task-local final. Existing original-result retrieval is bounded to 16 KiB without cursors, not a full-result archive. Retain complete attributable output, when available, in the immutable task-thread delivery payload, not the bounded report or work-record JSON. Retention/capacity must cover retained task obligations and history, including after resource release; missing, oversized, truncated, or unretained output stays honestly incomplete/held.

`recoverTaskReport(taskId)` is the authenticated observational recovery contract, including after observer removal. Resolve stored original identities, retrieve their trusted original result through `SessionPort`, then revalidate identity and obligation revision inside the DB transaction/CAS. Reconcile the same logical obligation and atomically persist its immutable correlated supplemental intent. Duplicate evidence converges on that identity; conflicting evidence holds. Preserve old admission, consumption, and delivery facts without reopening execution, adding an observer, editing old physical messages, or prompting for the latest assistant answer.

Observation, session restoration, original-result retrieval/publication, and model continuation are distinct. Bounded original-evidence reconciliation precedes owner escalation; it sends no prompts or tools. New prompts/model continuation require authorization within the mandate, which may already authorize ordinary turns without fresh approval each time. Never reconstruct or re-execute tools from transcripts: missing or error tool results can coexist with committed effects, and no exactly-once-effects guarantee follows. Automatic crash continuation and original-output availability after retirement remain unproven.

Execution capacity/session/worktree release requires exact authoritative terminal proof for the original attempt plus safe verified ownership and closure; report/control debt and dedupe history remain durable. Local end timestamps, a dead/disowned/lost host, or an administrative disposition are insufficient. Every retirement/rebind path, including forced and bulk `allDead` cleanup, must enforce this predicate. Only genuinely unsent controls may become not-delivered on exact terminal proof; uncertain sends cannot be relabeled unsent. `/cancel` records a held local operator request, not proven remote cancellation, and opens no private GJC abort path.

**Cockpit and bounded context.** Produce uncached on-request views over existing task/attempt/control/report/delivery records and source-linked immutable briefs/decisions, not consuming inbox reads or a transcript archive. Include a source-revision manifest, evidence/observation times, separate render time, completeness, and omissions. External evidence not reconciled to the DB snapshot is labeled raced/stale/unavailable; rendering never makes old evidence fresh. Contradictory sources retain provenance. Re-read before an action requiring current state.

Initial selection bounds are at most 20 tasks and 16 KiB UTF-8 per cockpit view; exceptions first, then stable task-ID order. Task detail selects at most 50 source records and 16 KiB, ordered by sequence with ID tie-breakers. State bounds and known omission counts, or explicitly unknown completeness; never truncate an identity into apparent validity. A changed revision manifest makes continuation a new snapshot. Source-linked cross-session context remains rough evidence, not authoritative memory or recipient instructions; inferred decisions need owner confirmation.

The cockpit names exceptions, task/source links, and outstanding owner actions; deeper bounded discussion is retrieved on request or concrete explanatory need. The original task answer publishes to its mapped thread independently of coordinator report admission; the agent's review reads the complete retained answer before recording its disposition, and genuine owner questions are durable records. An outstanding review stays visibly pending and is surfaced only on existing coordinator turns; there is no automatic clearance notice, reminder turn, or scheduled digest, and eventual review is not guaranteed. In Discord mapped task threads, slash commands are explicitly refused with full support backlogged; ordinary slash commands elsewhere are unchanged.

Qualification must cover crash/race publication, uncertain controls, retention, and every retirement route. Existing per-observer containment must isolate a corrupt/torn task beside a healthy active lane during both timer observation and restart recovery: bounded matching-lane diagnostics/observer removal, no unhandled rejection or gateway exit, healthy terminal/report settlement, and the corrupt original held without replacement/replay. Generic corrupt-row rejection alone is insufficient.

**Ordinary unbound lanes.** The existing mechanisms below remain the substrate, not an escape from the stronger Firstmate task fences above. Their generic parent fallback and dead-session retirement rules do not authorize mapped-task detail fallback or task-resource release without exact terminal proof.

`work.start` binds a gateway-created `work/task/<name>` origin hosted by the shared user broker in the coding register and returns after acceptance proof, without waiting for completion. An accepted receipt is not a completed task. Its optional `model` is a model ID or `{ "preset": "name" }`; the selection is applied at `session.create` and re-applied on each send. Admission is capped by `work.maxLanes` (default 8). A new name at capacity fails with `lane_capacity` carrying `{maxLanes, active, candidates[]}`, with candidates sorted idlest first; an already-bound name is always admitted by the capacity check.
Each start/wake send prepends a lane notice to the first accepted send in a session epoch, and repeats it if the parent or nested-work policy changes; the notice identifies the parent-report path and forbids direct chat posting. Runs carry no lane notice.

`work.status` is a read-only durable snapshot plus a live query of the matching operation, not an atomic distributed snapshot; it never binds, attaches, refreshes activity, settles an attempt, or acknowledges a hold. Job state, attempt end state, and broker operation status remain distinct. `work.steer` targets only the current open attempt without rebinding; an ambiguous steer reports `work steer acceptance uncertain` and must not be automatically retried with a new reference. An open attempt blocks another start/run, including `resume:true`, and retirement. Synchronous `work.run` uses the same lifecycle but waits only for a response and never reports to a parent. Start and run from a lane session are refused unless `work.allowNested=true`. Caller timeout, disconnect, or gateway shutdown detaches the waiter without settling or aborting the worker. A timed-out run reports `work wait timed out; attempt remains observable`.

The durable observer recovers the original operation/session identity on startup and broker-generation changes, without resend, bind, or replacement. A live matching operation reported as `unknown` is neither acceptance nor terminal proof: keep observing without overlap. A torn send without acceptance proof reports `work send acceptance uncertain`, not a successful receipt. Trusted terminal evidence can finish reconciliation without live reattachment. Without that evidence, unrecoverable dead/disowned/indeterminate recovery authority yields a fail-closed `terminal_uncertain` operator hold; a local end timestamp does not prove the worker stopped. Transient transport loss is not a worker deadline, and repository progress does not clear a sticky uncertainty/failure hold.

Both work verbs accept `callerSessionId`, forwarded by the CLI from `GJC_SESSION_ID`. It is an untrusted routing hint on the owner-trusted socket: socket clients are owner-equivalent, so the nested-lane gate is policy, not a security boundary. Start parent resolution prefers a recognized persona caller, then a permitted lane caller; if neither applies it falls back to `ownerTarget`, and otherwise has no parent.

Lane report text uses `[lane <name>] completed|failed|attempt_ended: …` with bounded, safe content, never raw SDK exceptions. Cancellation and incomplete outcomes are not success. Uncertain/missing-receipt reports say `attempt_ended` plus the true safe reason while retaining the actual end state and hold. Completed work whose answer cannot be proven says `completed: output_unavailable`; synchronous `work.run` remains response-only and reports `work output unavailable` to its caller without rewriting known broker completion. Uncertain/incomplete reports with unavailable output include both the outcome reason and `output_unavailable`. A terminal first reported with `receiptState=missing` is not final: the SDK can attach the final body with a late `agent_end`, so output reads keep polling within their bounded budget. A proven same-op final body upgrades the stored terminal to `present` and settles `completed` exactly once. If the receipt remains missing after the budget, the report says `attempt_ended: terminal_missing_receipt: final_response_missing opRef=<opRef>`; this means the SDK recorded no final response text, not that commits or PRs were lost, and it does not verify them.

A settled start result is reported to its selected parent as an internal lane report turn, not as a human message. Persona parents receive an internal inbound row; lane parents use the durable lane-report inbox, which steers an open parent attempt or wakes a new one when `work.allowNested` is enabled. Reports follow the formal lane -> persona -> human path. A run is response-only and never reports.

If parent admission fails, the report uses exactly one fallback delivery-ledger row; the physical post is at-least-once, so a crash after posting may produce a duplicate. A parentless result is durably `no_target`. Pending, claimed, held, and undeliverable lane reports are visible through `work jobs`; its `reports=p:N c:N h:N u:N` counts are printed when any count is non-zero. Ambiguous delivery remains held, and a report with no root fallback is marked undeliverable.


Worker output requires proven attempt-final attribution and complete original content: a timestamp alone, a neighboring prior reply, intermediate tail text, completed pagination, or a summary is not proof. The exact pre-send floor has no two-second tolerance. Intentional silence is recognized from the proven original final body before prefixing or truncation, persisted before dependent tail checkpoints, and suppresses lane reports even if later text is unavailable or authority uncertain. Missing provenance means unavailable output, not assumed silence. Post-terminal output acquisition has three durable reads across restarts (immediately, then after 1 second and 5 seconds); invalid attribution or definitive unavailability ends retrieval early. This finite retrieval budget starts after terminal proof and never limits worker duration.

`work.retire` closes only a positively owned, gateway-created gjc session with `session.close` and bumps the origin epoch, so the next start/run creates a fresh session. Retirement is fail-closed on ownership: it refuses while the lane job has an open attempt, while the job record is corrupt, and while the last attempt ended without trusted broker proof until the operation is proven terminal or the broker reports the session dead. In particular, `terminal_uncertain` is not proof of stoppage. A failed `session.close` releases the slot only when broker liveness proves the session gone; otherwise the binding is retained and the refusal names the close error, because an uncounted live worker is the exact failure the governor exists to prevent. The 60-second sweep nominates lanes idle for at least `work.idleRetireMs` (default 6 hours, measured from the last attempt's end) or whose lane job is `done` or `aborted`, and each nomination is re-proven under the lane lock against the session id it was selected with, so a lane reused or rebound meanwhile is left alone. The gateway never performs global GC or `session.delete`; retirement bounds owned live worker hosts, not the user's saved-session index.

`ops.cycle` reports `lanes: {active, max}` and gates on `lane_capacity_exhausted` when the cap is reached. A retired lane keeps its `work/task/<name>` row unbound; that row is healthy only while a settled lane job (`attempt_ended`, `done`, `aborted`) vouches for it. The same unbound shape with no job (a failed first bind) or with a `running`/`awaiting_operator`/`stalled` job (a crash-left or held worker) stays a `stale_session_identity` gate. The ActionGuard system notice recommends start/status/steer for delegated long work and forbids direct `gjc` launches from persona turns as prompt guidance, not a new command-enforcement hook. Workers share the user's broker but remain separately owned gateway sessions; unrelated user sessions are never adopted. Host skill/script replacement, deployment, and process cleanup are separate operational work, not part of the worker-lane API change.

Worker-lane logs are grep-stable:

- `lane_retired name=… session=… reason=operator|idle|job_done|job_aborted closed=…`
- `lane_close_failed name=… session=… detail=… action=retained|session_gone`

The persona preamble comes from `SOUL.md`, `AGENTS.md`, and `USER.md` in `$GAJAEWAY_HOME/workspace`; the same directory is passed to `gjc` as the session working directory.

The first attempted turn in every origin epoch also receives a trusted `Session bootstrap` system section. Its stable ID is derived from the opaque origin key and epoch. It carries current conversation metadata plus bounded navigation from `$GAJAEWAY_HOME/memory`; it is never placed in unread/user text. The serialized section is capped at 8 KiB by UTF-8 bytes. Identity is mandatory, today and yesterday receive bounded priority shares, and recoverable channel/rules/navigation pointers consume only the remainder. Daily sources alone may be labelled newest-entry excerpts and have a 4 MiB read ceiling; other sections remain whole. Excerpts, read-ceiling drops, and budget omissions all set truncation and are named explicitly. Source paths are realpath-confined to the resolved memory root, so a configured root symlink and in-root canonical symlinks work while traversal and escaped symlinks are rejected. Public/group turns require explicit full-origin association for channel/project/task/handoff material, exact-origin filtering for daily entries, and an explicit `bootstrap-safe: public` or `bootstrap-visibility: public` marker before associated document bodies are admitted. Included source material is delimited as reference data, never executable instruction text.

Bootstrap completion is durable in schema 14. An epoch is pending while `epoch > last_bootstrapped_epoch`; `/new` establishes pending state in the same session-row update that bumps the epoch. The gateway commits the projection only after a terminal text or intentional-silence success. A failure before terminal success retries with the same stable bootstrap ID. If an intermediate reply was already delivered before failure, the unread body is consumed to prevent a harmful answer replay, while the still-pending bootstrap is safely re-presented under that same idempotent ID on the next turn. Session and ops projections expose only epoch, applied time, included section names, byte count, truncation, and diagnostics—never source bodies.

## Delivery and crash semantics

Before an outbound reply is emitted, the gateway creates a durable ledger item. States are `pending`, `inflight`, `confirmed`, `failed_ambiguous`, and `expired`. Adapters mark an item inflight before attempting platform delivery and confirm it after success. A non-ambiguous failure returns to `pending` with exponential backoff (2 seconds, doubling to a 5-minute cap); the fifth definitive failure expires it. An ambiguous failure stays `failed_ambiguous` regardless of its failure count. Any unsettled item older than the 24-hour freshness window expires during a delivery sweep.

At negotiated connection time and every 15 seconds while an adapter is connected, adapters receive due unsettled deliveries. This is deliberately at-least-once delivery: an `inflight` or `failed_ambiguous` item is reissued with `redelivered: true` and `duplicateWarning: true`. Platform adapters must display the duplicate warning. Confirmed or expired records are not replayed automatically; expired counts and the five most recent identifiers/origins are exposed by `gateway.status`, and the admin console raises attention. Expiry is logged and an owner-target notice is sent once per delivery when configured. Operators can requeue eligible rows with `gajaeway ops redeliver <deliveryId>` or `gajaeway ops redeliver --since <iso>` (selecting rows updated since that timestamp). Confirmed records are never requeued; old confirmed records are pruned after seven days.

## Engagement and safety floors

Existing Telegram topic-parent inheritance is preserved alongside thread-parent inheritance. The selected boundary policy can also supply `botAudienceMaxConsecutiveTurns` and `botAudienceMaxTurnsPerWindow`; an exact or parent policy replaces that whole entry, so omitted budgets then use global defaults rather than lower-priority boundary fields.

Loopback is trusted locally, while DMs continue to use `dmPolicy` and never inherit a group boundary. Group traffic uses one gateway-owned channel policy: `engagement` is exactly `open`, `mention-open`, or `closed`, and `audience` is independently `all`, `human-only`, or `bot-only`. `open` admits matching-audience chatter; `mention-open` requires a real mention or native reply to this bot; `closed` ignores audience and requires both addressing and the existing owner/allowlist authorization. Omitted engagement remains closed. For `open` and `mention-open`, an explicit `human-only` audience excludes bots, while an omitted audience preserves legacy behavior: humans follow the engagement mode and bots use the closed, addressed-and-authorized gate. Omission is not equivalent to explicit `human-only`; `closed` always uses its addressed-and-authorized gate regardless of audience. Resolution selects one whole entry in order: exact channel/thread entry, immediate parent-channel entry for a thread, then a matching platform-qualified `boundaries` entry named by `boundaryId`; with no match, policy is closed. An explicit empty `{}` or `engagement: "closed"` entry is a match and suppresses inheritance; fields are never merged across entries. The guild boundary only controls admission for group messages the adapter can already see: it grants no Discord permissions and does not enumerate channels or expand discovery/recovery. Uncategorized channels can use the same fallback when their origin carries the guild boundary ID.

Discord drops self-authored messages before forwarding and the gateway durably deduplicates platform message IDs. Bot turns admitted through an explicitly widened audience have no consecutive-turn cap by default: `audience: "all"` means bot messages are turns, so several agents can collaborate in one thread. Two budgets bound them. `botAudience.maxConsecutiveTurns` (global) and `channels.<key>.botAudienceMaxConsecutiveTurns` cap consecutive bot turns per conversation when set, and a human message resets that count. An always-on rolling-minute rate limit (`botAudience.maxTurnsPerWindow`, default 30 admissions per conversation) is what stops a runaway bot-to-bot loop; a human message does not reset it. Rate-limited and budget-spent declines are logged with the origin, its current consecutive and windowed counts, and are projected by `gateway.status` as `engagement.botAudienceDeclines` and `engagement.botAudienceRateLimited`.

The gateway gives `gjc` unoverridable ActionGuard guidance. It forbids unrecoverable commands such as recursive removal of `/`, filesystem formatting, raw device writes, and fork bombs. It also refuses recursive deletion of `$HOME` itself or absolute paths outside `$HOME` and `$GAJAEWAY_HOME`. These are floors, not a configurable permission bypass.
